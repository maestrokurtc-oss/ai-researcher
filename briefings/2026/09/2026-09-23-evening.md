### [WordPress 인증 없는 경로 순회 취약점, 조건부 원격 코드 실행 가능](https://news.hada.io/topic?id=34160) ⭐️ 8.0/10

WordPress의 get\_page\_template\(\) 함수에서 인증 없는 공격자가 활성 테마 디렉터리 외부의 읽기 가능한 로컬 .php 파일을 포함시킬 수 있는 경로 순회 취약점\(CVE-2026-87902, GHSA-7hp8-65ch-5whp\)이 발견됐다. CWE-98로 분류되며 CVSS 4.0 기준 9.2점\(Critical\)로 평가됐고, 공격 자체는 네트워크로 사전 권한이나 사용자 상호작용 없이 실행 가능하지만, 원격 코드 실행\(RCE\)으로 이어지려면 활성 부모 또는 자식 테마 최상위에 page-로 시작하는 디렉터리가 존재해야 하는 조건이 필요하며 이는 Twenty Twelve, Twenty Fourteen 같은 구형 기본 테마와 Neve, Hestia, Sydney 등 인기 서드파티 테마에서 성립한다. 서버 측에서는 공격자가 지정한 .php 파일이 존재하고 웹 서버 계정으로 읽을 수 있어야 하며, register\_argc\_argv가 On으로 설정된 환경에서는 pearcmd.php를 이용한 RCE 전환이 가능하고, 공식 Docker PHP 이미지와 PHP 8.5 미만을 쓰는 기본 cPanel 설정도 영향을 받는다. 이 문제는 WordPress 7.1.2에서 수정됐고, 이전 버전 사용자를 위해 7.0.6부터 4.7.37까지 모든 이전 브랜치에 백포트 패치가 배포됐다.

**「배경」** get\_page\_template\(\)은 WordPress가 특정 페이지에 사용할 템플릿 파일을 찾는 내부 함수로, CWE-98은 PHP의 include/require 등에 전달되는 파일명을 적절히 제한하지 않아 임의 파일 포함이 가능해지는 취약점 유형을 가리킨다. pearcmd.php는 PHP에 기본 포함된 PEAR 패키지 관리 스크립트로, register\_argc\_argv가 활성화된 환경에서 파일 포함 취약점과 결합될 경우 원격 코드 실행으로 확장되는 알려진 공격 경로로 자주 언급된다.

**「영향」** Twenty Twelve, Twenty Fourteen, Neve, Hestia, Sydney 등 해당 테마 구조를 사용하는 WordPress 사이트 운영자는 서버 실행 환경\(register\_argc\_argv, PHP 버전 등\)에 따라 RCE 위험에 노출될 수 있으므로, 4.7 이상 모든 브랜치 사용자는 각자의 백포트 버전으로 즉시 업그레이드해야 한다.

### [jgrep: diff로 실행할 테스트를 Jev 모델에게 물어보는 CLI](https://news.hada.io/topic?id=34173) ⭐️ 6.0/10

jgrep는 예/아니오 확률만 반환하는 TypeSafe Jev 모델을 활용해 코드 검색과 테스트 선택을 자동화하는 CLI 도구다. --diff 옵션은 영어 한 문장으로 규칙을 적으면 PR에 해당 패턴 코드가 포함되었는지 확인하며, grep과 동일한 종료 코드\(0 매치/1 없음/2 오류\)를 반환해 CI에서 PR을 막는 용도로 쓸 수 있다. --tests 옵션은 diff를 분석해 관련 테스트 파일을 골라주는데, hono·zod·fastify·flask·requests의 실제 커밋 60개로 검증한 결과 전체 테스트의 12%만 실행해 작성자가 수정한 테스트의 92%를 찾아냈고, 파일명·import 기반 방식은 43%에 그쳤다. 60개 커밋 처리에 총 $0.11, 커밋당 약 1초가 소요됐으며, 이는 작성자가 실제 수정한 테스트를 얼마나 재현했는지를 본 결과로 필요한 테스트를 92% 골라준다는 의미는 아니고, 라이브러리 전반의 대규모 통합 테스트는 놓칠 수 있으며 검색 대상 코드 청크가 TypeSafe API로 전송된다는 한계도 있다. 설치는 npm i -g jevgrep &amp;&amp; jgrep init으로 가능하며, 벤치마크 방법과 커밋별 결과는 GitHub 레포의 bench/tests/에 공개되어 있다.

rss · GeekNews · 9월 23일 12:45

**「Jev 모델이란」** Jev는 TypeSafe가 만든 System One 모델로, 텍스트를 생성하는 대신 질문에 대해 예/아니오 확률, 여러 선택지 중 하나, 혹은 척도 상의 위치 중 하나로만 답을 돌려주는 경량 분류 모델이다. 일반적인 호출은 약 100밀리초 내외로 완료될 만큼 빠르고 저렴해서, 프론트 모델을 대체하기보다는 저비용으로 먼저 걸러내고 어려운 경우만 큰 모델에 넘기는 캐스케이드 구조에 적합하다. jgrep은 이 예/아니오 확률 응답 방식을 코드 청크 단위 검색과 테스트 파일 선택에 응용한 도구다.

**「영향」** CI 파이프라인에 --tests를 도입하면 전체 테스트의 12%만 실행해도 실제로 수정된 테스트의 92%를 찾아내 테스트 실행 시간과 비용을 크게 줄일 수 있어, 대규모 테스트 스위트를 가진 오픈소스 프로젝트나 팀에 실질적인 이점이 된다. 다만 큰 통합 테스트를 놓칠 수 있고 코드 청크가 외부 TypeSafe API로 전송되므로, 보안이 민감한 사내 코드베이스에서는 도입 전에 데이터 유출 위험과 실제 커버리지 손실을 별도로 검증해야 한다.

**「방안」** Eric Nguyen에 따르면 GLM의 도약은 자연어 LLM처럼 긴 문맥\(long-context\) 처리 능력에서 비롯됐다. DNA는 알파벳이 ACTG 네 글자뿐이지만 서열 길이가 평균 유전자 6만 염기, 길게는 230만 염기, 전체 인간 게놈은 약 30억 염기에 달해, 프론티어 LLM들이 100만 토큰 문맥을 다루기 훨씬 전인 약 3년 전부터 이미 긴 문맥 아키텍처\(예: striped hyena 계열\)를 통해 이런 규모를 처리할 수 있었다고 설명한다. 그는 이 모델들이 유전자와 단백질 코딩 부위 같은 DNA 내 명확한 신호 덕분에 RNA·단백질 등 여러 '언어'로 자연스럽게 일반화하며, 이는 3D 단백질 구조나 후성유전학, 자연어 같은 다른 모달리티 학습 이전에도 나타나는 특성이라고 주장한다. 핵심 실험은 RNA 압타머\(aptamer\) 데이터셋에서 낮은 점수부터 점진적으로 높은 점수로 이어지는 서열들을 모델에 보여주고, 아직 본 적 없는 최고 성능 서열들의 패턴을 스스로 이어가도록 요청한 것이다. Nguyen는 모델이 실제로 보여주지 않은 고득점 구간을 재현해냈다고 밝히며, 이를 자연어 LLM의 chain-of-thought에 대응하는 'DNA로 사고하기'라 표현한다. 그는 이런 장문맥·연쇄추론·다중모달 능력이 생물학적 문제 해결 능력을 끌어올리는 동시에 위험한 생물학적 설계 능력도 함께 키운다고 지적하며, 현재는 방어 역량이 공격 역량을 따라잡지 못하고 있다고 주장한다. 다만 구체적인 보안 위협의 세부 내용은 기사에서 공개되지 않아, 이 주장의 근거는 인터뷰 당사자의 서술에 의존하며 독립적 검증이나 반론은 제시되지 않는다.

**「시사점」** Nguyen의 핵심 논지는 GLM의 발전이 생물학 연구를 가속하는 동시에 오남용 위험도 키우는 이중용도 기술이며, 방어 역량이 뒤처진 지금 상황에서는 오히려 방어 목적의 프론티어 모델 개발을 더 밀어붙여야 한다는 것이다. 이는 사이버보안 영역에서 제기됐던 '공격과 방어 모두 프론티어를 따라가야 한다'는 주장과 같은 논리를 생물학 영역에 적용한 것이다.

### [Claude Opus 5.5 출시와 AI 모델 가격 인하 경쟁의 실체](https://www.latent.space/p/ainews-claude-opus-55-the-new-default) ⭐️ 6.0/10

rss · Latent Space · 9월 23일 06:41

**「배경」** Anthropic이 Claude Opus 5.5를 출시하며 Fable 5.1 수준의 성능을 Opus 5보다 40% 저렴하게 제공한다고 발표했고, 불과 한 시간 뒤 OpenAI도 GPT-6 Sol과 Luna를 각각 50% 낮은 가격에 내놓으며 정면으로 맞섰다. 저자는 이 두 발표가 헤드라인 성능 경쟁에서 가격 경쟁으로 초점이 옮겨가고 있다는 신호로 보고, 실제 비용 절감이 광고 문구만큼인지 따져본다.

**「방안」** 저자가 인용한 Artificial Analysis의 분석에 따르면 Opus 5.5의 토큰 단가는 입력/출력 기준 100만 토큰당 $5/$25에서 $4/$20로 20% 인하됐지만, 코딩 등 최대 성능\(max effort\)이 필요한 작업에서는 토큰 사용량 자체가 늘어나 이를 상쇄한다. 실제로 Intelligence Index 기준 task당 비용은 Opus 5의 $5.86에서 Opus 5.5의 $5.98로 오히려 소폭 상승했으며, 늘어난 토큰 사용량만으로는 비용이 80% 가까이 치솟았을 것을 가격 인하와 캐시 읽기 비용 절감이 겨우 상쇄한 결과다. 즉 “40% 저렴하다”는 주장은 기본\(medium\) 설정에서만 성립하며, 최고 성능 설정에서는 실질적 절감이 거의 사라진다고 저자는 지적한다. 반면 Fable 5.1 대비로는 Cline 등의 평가에서 비슷한 지능 지수를 약 2.5배 낮은 비용에 달성한다는 보고도 있다. 벤치마크 면에서는 CursorBench, FrontierCode, ParseBench 등에서 대체로 전작과 Fable 5.1을 앞서지만, ProgramBench 저자는 Anthropic이 전체 문제 중 어려운 하위집합을 제외한 서브셋으로 근접 100% 해결률을 보고했다고 지적하며 지표 해석에 주의를 당부한다. 글쓰기 품질 개선도 두드러진 특징으로, 정보를 앞부분에 배치하고 사용자가 지정한 작성 규칙을 잘 따르는 점이 실사용자들 사이에서 긍정적으로 언급됐고, 저자 자신도 AINews 섹션을 Opus 5.5로 즉시 전환했다고 밝힌다. 한편 OpenAI의 Sol과 Luna는 캐시 인프라 개선을 통해 캐시된 입력 토큰 읽기 비용을 최대 90%까지 낮추는 등 절대 성능보다 작업당 비용 대비 효율\(Pareto\) 개선에 초점을 맞췄다.

**「启示」** 저자의 핵심 논지는 두 회사가 내세우는 화려한 가격 인하 수치가 실제 워크로드, 특히 최대 성능이 필요한 작업에서는 토큰 사용량 증가로 크게 희석될 수 있다는 것이다. 모델을 선택할 때는 표면적 토큰 단가가 아니라 effort 설정별 실제 task당 비용과 벤치마크 서브셋의 구성까지 따져봐야 한다는 점을 시사한다.
